# 116.项目实战：产出 AI 冥想助手的计划与设计方案


## 本课总结

1. 宪章和规格确定后用 /speckit.plan 生成技术计划，把已确认的需求转成具体方案，只需懂每项技术解决什么问题。
2. 技术栈包括 Expo、expo-router、NativeWind、Reanimated、Lottie、Expo Audio、本地化与 i18next、EAS Build 等。
3. 计划前特意补一条约束：AI 能力要统一封装，不绑定某一家模型接口，方便以后更换大模型厂商。
4. Claude Code 逐个确认大模型在哪调用、语音输入怎么实现、白噪音从哪来，分别选客户端直连、系统识别、打包素材。
5. 计划阶段除 plan.md 外还生成 research、data-model、ai-provider、quickstart 等配套文档，记录调研与关键决策。
6. 命名调研后把产品名从 Breathe Now 统一替换成 Lumera，GitHub 仓库名可以继续用原来的名字。
7. 用 Taste Skill 按规格与计划生成 HTML 原型，补齐多语言、浅色模式并修好文字对比度后推送 GitHub 存档。

---

在宪章和规格确定以后，我们的下一步就是制定技术计划。Spec Kit 里我们可以用斜杠 /speckit.plan 来生成技术计划，这个技能会把前面确定的需求进一步转换成具体的技术方案。这一次我们会用到几项新的技术，但不需要知道技术细节或者具体的代码实现，我们只要了解它们分别解决什么问题就可以。

### 先认识这期的技术栈

App 方面我们还是用熟悉的 Expo，它可以让我们用同一套 React Native 代码同时开发 iOS 和 Android App。我们还会用到 expo-router，它主要负责管理 App 里的页面和跳转，比如从首页进入其他页面、在不同 Tab 之间切换，我们可以把它理解成 App 的导航系统。

页面样式方面这次我们会用 NativeWind，主要是因为写 UI 会更快。传统写法经常需要单独创建一大堆样式代码，而 NativeWind 可以直接在组件旁边写样式描述，比如颜色、间距、字号和布局等等。对 Vibe Coding 来说，这种写法的好处是 AI 更容易同时看到页面结构和对应样式，修改 UI 会更直接。

下一个是 Reanimated。这次我们要做冥想 App，动画会比之前重要很多，比如引导呼吸的光球要不断放大缩小、按钮要有反馈、页面切换也要更加顺滑。Reanimated 就专门负责这种跟用户操作和页面状态实时变化的动画，很适合做出流畅的交互效果。我们还会用 Lottie React Native，它同样是做动画，但和 Reanimated 的用途不太一样：Reanimated 更适合按钮反馈、光球缩放这种需要实时控制的动画，Lottie 更像一个现成的动画包播放器，可以直接播放准备好的动画文件。所以 Reanimated 更适合做交互动画，Lottie 更适合播放现成的完整动效。

接下来是 Expo Audio。我们的计时模式需要播放白噪音，而且用户还可以组合不同的环境声音，所以需要一个专门处理音频的工具。Expo Audio 是 Expo 提供的跨平台音频库，可以负责音频播放、暂停、循环的功能。

那因为这个 App 是面向海外用户的，所以多语言能力也要从一开始就考虑进去。这里我们会用到两个工具：expo-localization 负责读取用户手机当前使用的语言和地区，i18next 负责管理不同语言版本的文案。这样以后用户使用英文系统，App 就可以优先展示英文，切换成其他语言也不需要重新做一套页面。所以它们可以让 App 从一开始就具备出海需要的多语言能力。

最后是 EAS Build。前面我们自己打包过 Android APK，但真正准备给别人测试、甚至以后上架 App Store 和 Google Play 时，就需要更正式的构建流程。EAS Build 是 Expo 提供的云端打包服务，可以帮我们在云端生成 Android 和 iOS 安装包，也能处理一部分签名配置，给后面的真机测试和正式上架都做好准备。

### 开始生成技术计划

规格澄清完成以后，下一步就是生成技术计划。新建一个 Claude Code 会话，模式可以切换成 Auto Mode 自动模式，然后用 Spec Kit 的斜杠 /speckit.plan 命令。除了把前面介绍过的技术栈写进去，我还特别补了一条：AI 能力要做好统一封装。因为后面项目可能会更换不同厂商的大模型，所以最好不要直接绑定某一家模型接口。发送以后，Claude Code 会结合 spec.md 和这些技术要求生成 plan。这过程中它还提出了几个需要我们确认的地方。

### 大模型在哪里调用

第一个是 DeepSeek 应该在哪里调用。Claude Code 给了三个方案。第一个是 Expo Router API Route：我们可以直接在 Expo 项目里写一个服务端接口，让 App 先请求这个接口，再由接口调用 DeepSeek。这样 API Key 可以放在 EAS Secrets 里，不会暴露在手机端，而且不需要另外再搭一套独立后端。第二个方案是使用独立的轻量后端，比如 Supabase Edge Function，安全性没问题，但要额外维护一套部署环境。第三个方案是让 App 直接调用 DeepSeek，这个方式最简单，开发起来最快。我们为了先快速把功能跑通，可以暂时选择客户端直连，但因为 API Key 会被放进客户端，正式上线时有泄露风险，所以真正上线前还是应该把大模型调用放到服务端。

### 语音输入和白噪音怎么解决

第二个问题是语音输入怎么实现。Claude Code 也给了三个方向。第一个是直接用手机系统自带的语音识别能力，也是它推荐的方案。这样用户说话以后，手机就可以把语音转换成文字，不需要我们额外接一个收费的语音服务，成本更低。第二个方案是调用云端的语音识别服务，好处是识别效果通常更稳定，也更容易支持多语言，但要额外付费，还会增加一些网络延迟。第三个方案就是第一版先不做语音，只保留文字输入，这样开发最简单，但会损失一部分我们一开始设想的用户体验。综合来看我们还是选择第一种，这样既能保留语音输入，又不会让第一版变得太复杂。

第三个问题是白噪音从哪里来。Claude Code 给了几个方向：可以自己制作并打包进 App，也可以使用网上现成的音频素材，或者直接在线播放。我们这里让 Claude Code 帮忙寻找公开可用、版权明确的音频素材，再直接打包进 App。这样做的好处是：第一，用户不联网也能播放；第二，不依赖第三方在线播放服务，使用起来会更稳定。

### 计划和配套文档

计划生成完成以后，除了核心的 plan.md，Spec Kit 还帮我们补充了几份配套文档。我们先来看 plan.md，这是最核心的技术计划。打开以后可以看到，它会概括这一版产品的核心功能，然后把整个项目的技术方案定了下来，比如是用什么开发框架、各个工具选什么版本、数据存在哪里、怎么测试、最终运行在哪些平台，以及项目文件怎么组织。像我们前面确定的 Expo、expo-router、NativeWind、Reanimated、Expo Audio 等技术，也会在这里落成明确的技术决定。

这个阶段还同时生成了一份 research.md。这份文档主要记录 Claude Code 在制定计划时做过的技术调研和关键决策，比如不同技术应该选择什么版本、能不能互相兼容等等。以后如果想知道为什么当时这么决策，就可以回来看这份文档。接下来是我们比较熟悉的 data-model.md，也就是数据模型，它会把 App 里有哪些数据、它们之间是什么关系，以及哪些数据涉及隐私的问题整理清楚。

这次还多了一份 ai-provider.md。因为我们希望 AI 功能不要和某家模型绑死，所以会提前定一套统一的调用方式：现在可以用 DeepSeek，以后如果换成 OpenAI、Anthropic 或其他模型，也不用把整套逻辑重写一遍。另外还有一份关于数据格式约定的文档，主要是统一项目里的数据格式，比如预置数据怎么写、多语言字段怎么组织、保存在手机的数据用什么结构，这样后面不同功能处理同一份数据时，就不会各写各的格式。最后还有 quickstart.md，它可以理解成项目的快速启动说明书，主要记录怎么把项目运行起来、怎么验证主要功能，以及后面怎么打包测试。

### 把产品名称定下来

在做原型之前，我们先把产品名称确定下来，因为名字后面会出现在原型、文档和 App 里。Breathe Now 只是我们前期临时用的名字，如果以后真的准备上架，最好提前检查一下有没有同名或者高度相似的产品，避免后面再改名。所以这里我们先让 Claude Code 帮我们做一轮基础调研。发送之后，Claude Code 会去查 App Store、域名和公开搜索结果。调查下来，Breathe Now 已经被不少产品用过了，继续用这个名字会增加品牌冲突的风险，所以这里我们换一个。接下来直接采用它给出的其中一个名字，叫 Lumera，结合了光和空气的概念，比较符合冥想呼吸这类产品的气质，所以我们可以采用这个名字。

确认以后，Claude Code 会把项目文档里的产品名从 Breathe Now 统一替换成 Lumera，包括 README 和 GitHub 文档里的。它还提醒我们 GitHub 仓库目前还是原来的名字，那这里问题不大，因为 GitHub 主要用来存放代码和做版本管理，仓库名不一定要和最终产品名完全一致。另外目前项目还没有正式初始化 Expo 工程，所以后面创建 App，我们就直接用 Lumera 作为产品名称。

### 用 Taste Skill 生成原型图

产品方向确认以后，下一步是根据前面的规格和计划生成原型图。这次我们换一个设计相关的 Skill，叫做 Taste Skill，它主要用来提升 AI 在 UI 设计上的审美和判断，让生成出来的页面更有设计感。首先新建一个 Claude Code 会话，让它帮我们安装这个 Skill。安装过程中，Claude Code 会询问安装范围，这个我们选择全局安装，这样以后其他项目也可以继续使用。接下来还会问要安装哪些 Skill，这里可以直接选择安装它提供的全部 Skill，让设计能力更完整一些。确认以后等待 Claude Code 完成安装就可以了。结果安装完成以后需要新建一个会话才能用，我们这次要用的核心 Skill 是 Taste Skill 里的 design-taste-frontend。

接下来就让 Claude Code 来设计 App 原型图。在提示词里我们首先指定了要用的设计 Skill，然后让它参考前面已经确定好的产品规格和计划方案，同时规定原型图统一放到项目的 prototype 文件夹里，方便后面继续开发。发送之后我们等待生成完成。搞定以后，Claude Code 会把原型图放到 prototype 文件夹里，同时还生成了一份设计说明文档。

### 看一遍原型效果

我们先看 HTML 原型图：点击会话里的 index.html，打开文件后再点击右上角的预览按钮，就可以把页面渲染出来。整体效果还是很不错的，Taste Skill 还结合了 Lumera 这个名字里光的含义，所以页面用了不少温暖柔和的配色方向。首先在 Home 首页可以看到两个核心功能：引导呼吸 Breath 和专注 Focus。我们先进入 Breath，这里可以输入自己当前的感受，也可以直接选择焦虑、紧张、疲倦这种状态。选择完成以后点击下面的 Find My Breath，开始之前会先出现一段引导说明，用户看完以后就会进入正式的呼吸引导页面：吸气时光球逐渐变大，接着屏息保持，再缓慢吐气，吐气时光球逐渐缩小，然后再次进入屏息和下一轮呼吸。

接下来我们进入 Focus，也就是白噪音专注计时器，看下效果。用户可以先选择专注时长，再自由地添加不同的白噪音，比如雨声、风声、海浪声，还可以分别调节每个音源的音量。设置完成以后点击开始专注，就会进入计时页面，并按照我们选择的时间开始倒数。目前看起来整体功能和样式都没什么问题。

最后我们再看 Claude Code 同时生成的那份设计说明文档，里面记录了原型的整体配色、字体选择、动画处理等设计决策。如果想快速了解原型背后的具体设计决策，就可以看这份文档。

### 补充细节页面并推送版本

在这个交互原型上，我们还可以继续补充一些完整产品常见的设计，比如浅色模式、首次打开 App 时的 onboarding 介绍页，以及多语言切换。那这里直接把需求发给 Claude Code。发送以后 Claude Code 会开始补充这些页面和交互，我们稍等它修改完成。更新后的原型一打开就会先进入 onboarding 页面，整个 App 的完成度会更高，同时还支持英文、西班牙文、中文三种语言切换，以及深色、浅色两种显示模式。

浅色模式是这次新加的，那相比深色模式，它的光效会弱一些，整体看起来更素雅。不过测试的时候我们发现，浅色模式下有些文字颜色和背景对比不足，已经看不清楚，所以继续让 Claude Code 优化。发送以后，Claude Code 会根据这个问题调整浅色模式下的文字样式。我们等它修改完成，完成以后再检查，发现还有部分文字颜色太浅。这时候就不要只抛出一个模糊的问题了，我们直接告诉 Claude Code 具体页面和具体内容，帮助它更快定位。然后我们再等 Claude Code 完成修改，重新打开页面，可以看到浅色模式下这些文字已经变成更合适的颜色，预览体验正常了。到这里，我们原型里的多语言切换、浅色模式，以及浅色模式下的文字适配都补充完成了。

原型图调整完以后，我们就可以把这个阶段的项目代码推送到 GitHub，保存一个版本。这里直接让 Claude Code 帮我们完成提交和推送。发送以后，Claude Code 会整理当前改动并推送到远程仓库。我们等它操作完成，这样这个阶段的产品规划、原型设计和相关文档就都保存下来了。我们下期见。
