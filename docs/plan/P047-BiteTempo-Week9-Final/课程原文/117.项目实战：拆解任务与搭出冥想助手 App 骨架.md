# 117.项目实战：拆解任务与搭出冥想助手 App 骨架


## 本课总结

1. 任务拆解沿用改名、出计划的那个 Claude Code 会话，同一上下文能直接沿用已确定内容，上下文过长再考虑重开。
2. 用 Spec Kit 的任务拆解命令生成任务清单，可在提示词里引导顺序：先骨架，再混音台动画，后接 AI 与国际化部署。
3. 任务文档按 Phase 组织阶段，每个任务有 T001 这样的编号，后面开发时清楚做到哪个阶段、哪些已完成。
4. 拆解后再让 Claude Code 交叉检查文档，发现 AI 调用方式与呼吸法数量前后不一致，统一版本再进开发。
5. 用 Spec Kit 的实现命令按任务清单逐项开发，更严格地按文档推进，减少超出任务范围或做完缺验证的情况。
6. Phase 1 执行后发现实际目录与计划文档不一致，应以实际项目结构为准，同步修正 plan.md 和 tasks.md。
7. Phase 2 搭好骨架后用安卓真机构建运行，能看到 Breath 和 Focus 两个入口，后续功能再往骨架上填。

---

这一节我们会进行任务拆解，并且搭建出 App 的基础骨架。开始之前，我们先回到前面修改名称、产出计划的那个 Claude Code 会话。因为任务拆解会参考前面的规格和计划，所以相关联的工作可以先放在同一个上下文里，Claude Code 可以直接沿用之前已经确定的内容，不用我们反复解释。当然，如果上下文已经很长，重开一个会话也没问题，项目里的 Spec Kit 文档本身也会提供完整的信息。

### 拆解任务

Spec Kit 里拆解任务用的 Skill 是斜杠 speckit.tasks。为了尽快看到 App 大概的效果，我们还可以提前给任务顺序一些引导，比如这段提示词。这段提示词里，我们让 Claude Code 先初始化 Expo 工程、搭好 App 骨架，再做白噪音混音台和呼吸动画，之后接入 AI，最后再处理国际化和云端部署。但如果你还没有足够的技术经验判断顺序，也没关系，可以让 AI 先自己拆，再检查它给出的安排是不是合理。发送以后，Claude Code 会结合 spec.md、plan.md 和其他项目文档生成任务清单，我们稍等它完成拆解。

生成完成以后，打开 tasks.md，再点击拆分预览按钮查看，可以看到整体实现顺序和我们设想的基本一致，不过 Spec Kit 的拆解依旧把 Expo 初始化和 App 骨架拆成了不同阶段。

### 任务文档的组织方式

在 tasks.md 里，每个阶段叫一个 Phase，Phase 下面再拆成具体任务。每个任务都会有类似 T001、T002 这样的编号，其中 T 代表 Task，后面的数字就是任务编号。这样后面开发的时候，我们就很清楚当前做到哪一个阶段、哪些任务已经完成了。

任务拆解完成以后，我们又让 Claude Code 把文档整体交叉检查一遍。发送以后，Claude Code 会交叉检查前面生成的几份文档，我们稍等它完成分析。然后 Claude Code 提出两个比较关键的问题。第一个是 AI 调用方式前后不一致：spec 里还写着上传到云端处理，但我们后来在制定 plan 的时候已经决定，开发阶段先由客户端直接调用 API，所以这里要把 spec 同步更新。第二个是呼吸法库的数量不一致：plan 里显示的是 6 到 8 种，但 spec 和 tasks 里只写了三种，需要统一成一个版本。

### 修复文档冲突

这里 Claude Code 建议我们用 Spec Kit 的修复命令来处理。这个命令通常需要先讲清楚具体要修改什么，如果什么都不写，它不一定知道是要新建一份 Spec 还是修改现在这份。所以我们再次输入 Spec Kit 的 /speckit.specify，Claude Code 先问我们要怎么处理。针对第一个问题，这里选择修复 001 现有 Spec。接下来它会继续确认呼吸法库的数量，这里有两个选择：要么把 plan 里的 6 到 8 种缩减到 3 到 5 种，要么把 spec 和 tasks 扩充到 6 到 8 种。我们以前面已经确定的计划为准，选择扩充。提交以后，Claude Code 会同步修改相关文档，我们等它把这些冲突处理完成。

修复完成以后，两个主要问题就解决了，Claude Code 还留下两个中等级别的问题。一个是暂停专注时，计时和白噪音是否也要一起暂停；另一个是多语言情况下的内容匹配还没有明确。这两个问题它都已经给出了比较合理的修改建议，所以这里我们直接让 Claude Code 按照建议补充进去。发送以后再等 Claude Code 把对应的 spec 和 tasks 补充完整。这样在真正开始写代码之前，我们就先把规格、技术计划和任务计划之间的主要冲突处理掉了，后面的开发也会更顺畅。

### 按 Phase 1 开始开发

之前进入开发阶段时，我们会用提示词让 AI 去实现某个功能；这次我们直接用 Spec Kit 的 /speckit.implement，按照前面拆好的任务开始开发。

发送以后，Claude Code 会先读取规格、计划和任务表，确认 Phase 1 包含哪些任务、有哪些前置条件，再按照任务清单逐项实现。我们等待它执行完成。相比直接告诉 AI 把这个功能做出来，先告诉 Spec Kit implement，会更严格地按照 tasks.md 推进，并且能结合前面的规格和计划检查结果，减少超出任务范围、或者功能做完却缺少验证的情况。

Phase 1 执行完成以后，Claude Code 又发现了几个需要确认的地方。第一个是项目实际目录和计划文档不一致：初始化 Expo SDK 57 项目以后，实际使用的是 src、app 根目录结构，而我们之前的 plan.md 里还保留着旧的路径设计，部分任务文档里的文件路径也没有完全统一。这种情况下，不应该为了迁就旧文档去改已经正常生成的项目结构，而应该以实际结构为准，把计划和任务文档同步更新。另外两个问题影响不大：一个是原计划里的动画插件方案现在已经不需要了；另一个是我们电脑上的 TypeScript 版本比计划里写的更新，也不影响项目继续开发。

所以这里主要处理第一个问题。我们先让 Claude Code 停下来，把 plan.md 按照实际项目结构修正。发送以后，先让 Claude Code 把计划文档里的目录结构和相关描述更新完成。不过只修改 plan.md 还不够，因为 tasks.md 里的文件路径也要保持一致，所以继续让它一起对齐。发送以后，Claude Code 会继续检查，修改任务文档里的相关路径，我们等它全部处理完成。那这样，实际的项目结构、plan.md 和 tasks.md 就重新保持一致，接下来就可以继续进入 Phase 2 的开发。

### Phase 2 骨架与第一次真机运行

第二阶段我们继续用 /speckit.implement，这一阶段主要是把 App 的基础骨架搭起来，完成之后就可以先把项目跑起来看看。发送以后，Claude Code 会按照 tasks.md 完成这个阶段的任务，我们等它执行和验证完成。Phase 2 完成以后，Claude Code 列举了一些暂时遗留的问题，不过这些主要是后续阶段才会实现的内容，目前不影响我们先把 App 跑起来。

接下来我们在安卓真机上测试一下。我这边已经通过 USB 把安卓手机连接到电脑，所以可以让 Claude Code 使用 Expo 的安卓运行命令，构建一个测试版本，然后安装到手机上。发送以后，Claude Code 会开始进行安卓原生构建，第一次构建通常会花一点时间，我们等它完成编译和安装。如果你没有安卓手机或者不方便使用真机，也可以直接用安卓虚拟机测试，提示词可以改成这样。

那现在 App 已经安装到我的手机上了，我们打开看看。因为这是没有通过应用商店正式发布的测试版本，所以手机在安装时会进行安全检查，确认安装包来源是我们自己构建的版本以后，就可以继续安装。安装完之后我们打开 App，目前能看到 Breath 和 Focus 两个核心入口。因为 Phase 2 主要完成的是项目骨架和基础结构，还没有正式开发具体功能，所以现在这些页面还不能完整使用。后面阶段我们会在这个骨架上继续实现白噪音、呼吸引导的功能，同时把外观逐步调整到和前面的原型图一致。到这里，Phase 2 的开发和第一次真机运行就完成了。我们下期见。
