# 115.项目实战：使用 Spec-Kit 开启 SDD 流程


## 本课总结

1. 本周实战以出海 App 为主题做 AI 冥想助手，冥想是海外已验证、仍在增长的赛道，差异点是按用户当下状态实时生成内容。
2. Spec Kit 用 uv 安装 Specify CLI，Spec Kit 是工具名，Specify CLI 是装到电脑上的命令，再用 specify init 初始化到项目。
3. 初始化后项目里出现 .specify 文件夹放模板脚本配置，.claude 文件夹放专门给 Claude Code 的 Skill。
4. 输入框里输斜杠 speckit 能看到对应 SDD 各阶段的一系列命令，先把 Git 和 GitHub 仓库配好方便留版本记录。
5. /speckit.constitution 生成项目宪法，提前写入医疗表述红线、Expo、国际化和中文朗读等项目规则。
6. 规格文档按编号放进 specs 下的独立规格包，比如 001-breathing-focus-modes，编号只区分需求与顺序不代表优先级。
7. /speckit.clarify 在 Plan 之前逐个澄清歧义，确认完推送远程；工具负责跑流程，我们负责把需求和验收标准想清楚。

这一周我们会以出海 App 为主题，做一款 AI 冥想助手。为什么选冥想呢？因为我们的目标是做海外产品，要更多关注海外已经被验证过的需求。2016 年全球冥想 App 市场规模预计达到 27 亿美元，并且未来几年会保持接近 15% 的年复合增长率，其中北美是最大的市场。所以冥想在海外是一个已经形成规模、而且还在继续增长的赛道。像 Calm、Headspace 这些头部 App，核心体验还是以提前制作好的冥想、睡眠和呼吸内容为主，而我们这次想加入 AI，让内容真正根据用户此刻的状态生成。比如用户输入 10 分钟后要上台、凌晨 2 点睡不着、或者被客户放了鸽子气得很生气，AI 会判断当前状态，选择合适的呼吸节奏，再生成一段针对这次场景的引导词。练习时屏幕上会有一颗跟着呼吸节奏起伏的光球，引导文字跟随节奏出现，再搭配用户选择的白噪音。所以这次我们要做的，是一个能根据用户当下状态实时生成专属呼吸练习的 AI 冥想助手。

### 安装 Spec Kit

安装这一步我们还是直接交给 Claude Code，不用打开任何相关网页。我们直接在 VS Code 里新建一个 Claude Code 的会话，然后告诉它去安装 Spec Kit。发送以后，Claude Code 会先检查当前环境。Spec Kit 官方推荐用 uv 来安装 Specify CLI，如果电脑里还没有 uv，Claude Code 也可以顺手帮我们安装上。uv 可以理解成一个 Python 包和工具管理器，这里主要用它来安装和管理 Spec Kit。环境准备好以后它会继续安装 Specify CLI。这里先说清楚，Spec Kit 是这套工具的名字，而 Specify CLI 是它实际安装到电脑上的命令工具，安装完成以后我们会通过 specify 这个命令来使用 Spec Kit。所以如果终端里能正常使用 specify，就说明 Spec Kit 已经装好了。

### 初始化到项目里

不过现在我们只是把工具安装到电脑上，还没有真正进入某个项目。那这里 Claude Code 也提示我们，下一步还需要运行 specify init，把 Spec Kit 初始化到我们的项目里。接下来我们给 Claude Code 指定新项目的位置：我把项目放在桌面的 Development 文件夹，项目名暂时叫 Breathe Now。这里直接告诉 Claude Code 在指定位置创建项目。

项目创建以后，我们用 VS Code 把它打开。点击左侧的资源管理器，再选择打开文件夹，找到刚才创建的 Breathe Now 项目，然后打开它。可以看到初始化完成以后，项目里会出现一个 .specify 文件夹，这里面放的就是 Spec Kit 的模板、脚本和配置。另外还有一个 .claude 文件夹，因为我们这次用的是 Claude Code，Spec Kit 会把专门给 Claude Code 的文件放进来。具体来说这些内容主要是以 Skill 的形式存在，相关文件夹会放在 .claude/skills 里面。

### speckit 命令族与仓库配置

接下来点击左侧的 Claude Code 图标，新建一个会话，再在输入框里输入斜杠 speckit，就能看到一系列 speckit 的命令，比如 /speckit.constitution、/speckit.specify、/speckit.plan 等等。这些命令其实就对应 SDD 的不同阶段。也就是说，speckit 把我们之前手动走过的 SDD 流程直接做成了一套可以调用的指令。

目前这个项目只是完成了 Spec Kit 的初始化，还没有正式开始开发。这里建议先把 Git 和 GitHub 配置好，让后面每次修改都能留下版本记录，出了问题也方便回退。我们直接让 Claude Code 帮我们创建一个仓库并且推送到 GitHub。执行过程中，Claude Code 会问我们仓库要设置成公开还是私有，这里选择 Private 就可以，如果以后想把项目开源再选择 Public。它还问要不要创建 README.md。README 可以理解成项目的说明书，别人打开 GitHub 仓库以后通常第一眼就会看到它，里面一般会写项目是做什么的、怎么安装和运行。这里让 Claude Code 帮我们设置一个简单版本就可以。等 Claude Code 提示仓库已经创建并成功推送到 GitHub，这一步就搞定了，接下来我们就可以开始走 Spec Kit 的 SDD 流程了。

### 创建项目宪法

第一步先创建项目宪法，这里我们用 /speckit.constitution。它专门用来定义整个项目后续要遵守的原则和开发约束，并且后面可以直接跟上我们对这个项目的要求。因为我们做的是冥想，没有医疗资质，所以提前把医疗相关的表述设定红线，避免后面 AI 在文案和功能设计里越界。同时我们也把 Expo、国际化和中文朗读这些项目的规则一起写进去。

发送以后，Claude Code 会根据这些要求生成项目宪法。生成完之后可以直接点击返回的文档链接查看，也可以在项目的 .specify/memory/constitution.md 打开，Spec Kit 官方默认就会把项目宪法保存在这里。打开以后可以看到，Spec Kit 生成的宪法会更结构化，核心原则、工程约束、合规要求和治理规则都会整理清楚。这样后面写 SPEC、PLAN 和 TASKS 的时候，Claude Code 都有一套统一的项目规则可以遵守。

### 写规格文档

项目创建完成以后，下一步是写规格文档。那我们先规划这个产品要解决什么问题、有哪些功能，以及希望用户获得什么样的体验。我们这次的 App 叫 Breathe Now，它主要有两个模式。第一个是输入模式：用户可以通过文字或者语音告诉 App 自己此刻的状态，比如马上要上台演讲，或者睡前思绪停不下来。App 会根据这个状态匹配一种常见的呼吸练习，再生成对应的引导内容。练习过程中屏幕上会有一个跟随呼吸节奏起伏的光球。第二个是计时模式：用户可以设置一段专注时间，同时使用白噪音混音台，把不同的环境声音组合成自己喜欢的背景音。这次我们还希望整个 App 的视觉更有灵动感，尤其是页面切换、按钮反馈和呼吸光球这些地方，要有比较明显的动画效果。

发送以后，Claude Code 会根据 Spec Kit 的规格模板生成初稿。生成过程中，如果有影响产品行为但我们还没有说清楚的地方，Claude Code 也会继续向我们确认。比如这里它问输入方式到底是什么，并且它给出了仅文字、仅语音，以及文字加语音几个方案。我们希望用户在不同场景下都能方便输入，所以这里选择文字和语音都支持。至于语音怎么转成文字、具体调用什么服务，这些属于技术实现，我们要到后面的计划阶段再决定。回答完这些问题后，它会补充并且更新刚才的规格内容，最后生成两份文档：一份是正式的 spec.md，另一份是用来检查规格质量的 requirements.md。

### 规格为什么按编号存放

这两份文件都会放在 specs/001-breathing-focus-modes 下面。我们以前自己做 SDD 流程时，一份 spec.md 就够了，为什么 Spec Kit 的还有 001，再单独建一个文件夹呢？因为 Spec Kit 管理的是一整套需求规格包，不只是单独一份文件。这次我们描述的是第一阶段需要完成的核心功能，所以把它放在 001-breathing-focus-modes 里。001 表示这是项目里的第一份规格包，后面的 breathing-focus-modes 是根据这次需求生成的名称。以后如果 App 上线后我们再增加一个相对独立的新功能，比如睡眠模块，又可以继续创建第二份规格包。这些编号主要用来区分不同的需求规格包和创建顺序，不代表优先级，也不意味着 002 要等 001 全部完成以后才能开始。

把每份需求放进独立目录还有一个好处：后面生成的技术计划、实现记录和任务清单，也可以继续放在同一个规格目录里。这样每个功能从需求到开发都有自己对应的位置。接下来我们回到左侧的项目目录，找到 001-breathing-focus-modes，打开里面的 spec.md，再用拆分预览模式查看。可以看到 Spec Kit 生成的规格非常结构化，除了整体需求描述，还会把用户场景、功能要求和验收条件整理出来，方便后面继续做 Plan 和 Tasks。然后我们再打开同目录里用于质量检查的 requirements.md。这份文件可以理解成一张规格质量检查清单，它会检查需求有没有写清楚、有没有歧义、验收条件是不是完整。因为 Spec Kit 本身的模板主要是用英文写的，所以第一次生成时 requirements.md 里可能会出现英文标题和内容，这里我们直接让 Claude Code 改成中文就可以。翻译以后检查内容本身不会变化，只是把英文说明换成中文，我们后面读起来会更方便。

### 用 clarify 澄清歧义

规格文档生成以后，我们再走一遍 Spec Kit 的澄清流程。这次我们直接输入 /speckit.clarify。发送之后，Claude Code 会通过 Spec Kit 重新检查当前的 spec.md，找出还不够明确、可能影响后续开发的地方，再逐个跟我们确认，把这些歧义在 Plan 之前尽量先解决掉。

执行以后，Claude Code 开始针对几个关键问题向我们提问。第一个问题是：用户输入文字或者语音后，应该在哪里理解用户状态和匹配呼吸练习？我们会用云端大模型 API 来完成，所以选 B。第二个问题是：用户输入的感受和语音转写要不要长期保存在云端？所以我们选择不留存，也就是 A。第三个问题是：呼吸过程中除了光球之外，要不要加入轻量的声音提示？这里我们希望视觉和听觉可以一起帮助用户跟上节奏，所以选择 C，允许加入柔和的自然音。第四个问题是：第一版要不要加入账号、社交、冥想课程、数据统计这些扩展功能？第一版我们还是聚焦输入模式和计时模式，先把核心体验做好，所以选择 A。

### 推送与本讲小结

这些问题问完之后，我们先把这个阶段的修改推送到 Git，还是直接让 Claude Code 帮我们完成。发送以后，等待 Claude Code 完成提交和推送。看到它推送到 GitHub，就说明这个阶段的规格文档已经同步到远程了。

到这里我们应该也能感觉到，Spec Kit 和我们前面手动走 SDD 流程，本质上做的是同一件事情：定规则、写规格、澄清需求、做计划、拆任务。区别在于，Spec Kit 把这些流程和文件结构提前整理好了，我们不需要每次都从零设计流程和目录结构。所以真正重要的，还是把用户问题、功能规范和验收标准想清楚。工具负责跑流程，我们负责做判断。我们下期再见。
